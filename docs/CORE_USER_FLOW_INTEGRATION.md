# Core user flow integration — Player, Coach, Facility

วันที่ตรวจ: 29 กันยายน 2026

## เป้าหมายและแหล่งข้อมูลกลาง

`bookings` เป็นแหล่งข้อมูลกลางของการใช้คอร์ท: ผู้เล่น วัน เวลา คอร์ท สาขา สถานะชำระเงิน และ attendance ส่วน `coach_bookings` เป็นนัดบริการโค้ชที่ต้องอ้าง `court_booking_id` สำหรับคำขอใหม่ จึงไม่มีการพิมพ์ชื่อสนาม วัน เวลา หรือราคาจากหน้าเว็บแล้วให้แต่ละฝ่ายถือคนละค่า

โฟลว์ใหม่:

1. ผู้เล่นจองคอร์ทและผ่านการตรวจชำระจน `bookings.status = confirmed`
2. ผู้เล่นเลือกโค้ชและเลือกจากรายการคอร์ทของตนที่ยืนยันแล้ว ระบบคำนวณเวลาจบตามแพ็กเกจ และใช้ราคาปัจจุบันจาก `coach_services`
3. ฐานข้อมูลตรวจเจ้าของรายการ สนามยังไม่เริ่ม โค้ชผ่านอนุมัติ แพ็กเกจเปิดอยู่ เวลาสอนอยู่ในช่วงคอร์ท/ตารางโค้ช และไม่มีนัดซ้อน
4. โค้ชได้รับคำขอและตอบรับ/ปฏิเสธได้จริง เจ้าของสนามเห็นป้ายโค้ชใน Booking Desk และตารางสนาม แต่ค่าสอนไม่ถูกรวมเป็นรายได้สนาม
5. วันใช้งาน โค้ชกดเริ่มและจบการสอน ส่วนสนามใช้เช็กอิน/จบการใช้คอร์ทเดิม ทั้งสองสถานะยังแยกความรับผิดชอบแต่ผูกกับรายการเวลาเดียวกัน
6. ผู้เล่นยกเลิกเฉพาะนัดโค้ชได้โดยไม่ยกเลิกคอร์ท หากยกเลิก/คืนเงิน/ไม่มาตามนัดที่คอร์ท ระบบยกเลิกนัดโค้ชที่ยัง active ตามไปด้วย
7. เมื่อเลื่อนคอร์ท ระบบเลื่อนนัดโค้ชตามเวลาเริ่มใหม่และตรวจตารางโค้ชใหม่ใน transaction เดียว หากโค้ชไม่ว่าง การเลื่อนคอร์ทถูกปฏิเสธทั้งชุด

## สิทธิ์และมุมมอง

- Player: เห็นเฉพาะคอร์ทและนัดโค้ชของตน สร้างคำขอจากคอร์ทที่ confirmed และยกเลิกนัดโค้ชของตนได้ก่อนเริ่ม
- Coach: เห็นเฉพาะคำขอของโปรไฟล์ตน ตอบรับ/ปฏิเสธ/เริ่ม/จบได้ตาม state และเวลา
- Facility owner: เห็นนัดโค้ชที่ผูกกับ tenant ของตนทุกสาขา เพื่อเตรียมคอร์ทและบริการ แต่ไม่ได้เปลี่ยนสถานะงานสอนหรือรับค่าสอน
- Staff: เห็นเฉพาะนัดที่อยู่ในสาขาที่ถูกมอบหมาย เหมือนขอบเขตรายการจองสนาม
- Super admin: นโยบาย marketplace เดิมยังอ่านและดูแลรายการทั้งหมดได้

โปรไฟล์โค้ชใช้ชื่อคอลัมน์จริงของ schema (`biography`, `experience_years`) และโปรไฟล์ใหม่กลับเข้าสถานะรอ Super admin อนุมัติ ไม่อนุมัติตัวเองอัตโนมัติ ส่วนหน้าแพ็กเกจสามารถเพิ่ม แก้ไข เปิด/ปิดรับได้จริง โดยราคาและระยะเวลานี้ถูกอ่านซ้ำฝั่งฐานข้อมูลตอนสร้างคำขอ

## Migration

ใช้ไฟล์ `supabase/migrations/20260929000000_integrated_coach_court_flow.sql` หลัง migration booking operations วันที่ 14 กันยายน ไฟล์เพิ่ม foreign keys, indexes, RPC ที่ตรวจสิทธิ์/สถานะ และ trigger sync การเลื่อน/ยกเลิก

ก่อน push production:

1. สำรองฐานข้อมูลและตรวจ `supabase migration list`
2. รัน `supabase db push --dry-run` และตรวจว่ามี POS, booking operations และ integration migration ตามลำดับ
3. Apply ที่ staging และทำ UAT ทุก role ด้วยบัญชีคนละ tenant/สาขา
4. Deploy แอปหลัง migration สำเร็จ เพราะหน้าตารางและ Booking Desk อ่าน columns/RPC ใหม่

## UAT ที่ต้องผ่าน

- ผู้เล่น A เลือกรายการสนามของผู้เล่น B ไม่ได้ แม้รู้ booking code
- client แก้ราคา/วัน/เวลาใน request ไม่เปลี่ยนค่าที่บันทึก เพราะ RPC อ่านจากฐานข้อมูล
- คอร์ทสั้นกว่าคอร์ส, โค้ชนอกตาราง, โค้ชนัดซ้อน, ผู้เล่นนัดซ้อน และคอร์ทไม่ confirmed ต้องถูกปฏิเสธ
- โค้ช B ตอบคำขอของโค้ช A ไม่ได้ และกดตอบรับซ้ำต้องไม่สำเร็จ
- Staff สาขา B มองไม่เห็นนัดในสาขา A; owner เห็นทั้ง tenant; tenant อื่นไม่เห็น
- ยกเลิกนัดโค้ชอย่างเดียวแล้วคอร์ทยังคง confirmed; ยกเลิกคอร์ทแล้วนัดโค้ช active ถูกยกเลิกตาม
- เลื่อนคอร์ทแล้วนัดโค้ชเลื่อนตามเมื่อโค้ชว่าง และ rollback ทั้งหมดเมื่อโค้ชไม่ว่าง
- เจ้าของสนามเห็นชื่อโค้ชในตาราง แต่รายงานรายได้สนามไม่รวมค่าสอน
- โค้ชเริ่มได้เฉพาะระหว่างช่วงสอนและจบได้หลังเริ่ม รายได้ประมาณการนับเฉพาะ `completed`
- ทดสอบสอง session สร้างคำขอช่วงเดียวกันพร้อมกัน ต้องสำเร็จเพียงหนึ่งรายการ

## ข้อจำกัดที่ยังตั้งใจคงไว้

- นัดเก่าที่สร้างก่อน migration ไม่มี `court_booking_id` ระบบไม่เดาชื่อสนามจากข้อความเพื่อ backfill ต้องตรวจและเชื่อมด้วยคนหากต้องการเก็บเป็นข้อมูลใช้งาน
- ค่าสอนยังเป็นยอดแยกที่ผู้เล่นตกลงชำระกับโค้ช ยังไม่มี payment ledger, gateway, refund และ payout จริงสำหรับ marketplace จึงแสดงเป็น “ประมาณการ” และไม่นับรายการ accepted/confirmed เป็นเงินรับแล้ว
- หนึ่งรายการคอร์ทรองรับนัดโค้ช active หนึ่งรายการ ถ้าต้องการหลายโค้ชหรือแบ่งช่วงในคอร์ทเดียวต้องออกแบบ participant/session model เพิ่ม
- ต้องยืนยัน SQL runtime/concurrency และ UI ทุก breakpoint กับ Supabase staging จริงก่อนเปิด production

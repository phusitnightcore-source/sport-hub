# SportHub POS — คู่มือและสถานะความพร้อม

อัปเดต 13 กันยายน 2026

## ผลตรวจ

POS เดิมมีขายสินค้า ตัดสต็อก ใบเสร็จ และเปิด–ปิดกะ แต่ไม่มีขั้นตอนรับเงินสด/เงินทอน พักบิล คืนเงิน แก้ไขสินค้า หรือเงินเข้า–ออกลิ้นชัก ยอดวันนี้อาศัยบิลล่าสุดเพียง 40 ใบ และรายงานกะที่ปิดแล้วแสดงสถานะเปิดผิด

รอบนี้เพิ่มหน้าเคาน์เตอร์ใหม่และกระบวนการข้างต้นแล้ว แต่ยังไม่รับรองว่าเทียบเท่า POS เชิงพาณิชย์ทุกความสามารถ หรือพร้อม production จนกว่าจะ deploy migration และผ่าน UAT จริง

## วิธีใช้งาน

1. เข้า **คลังสินค้า** เลือกสาขาแล้วเพิ่มสินค้า เลือกหมวดอาหาร เครื่องดื่ม อุปกรณ์กีฬา หรือพิมพ์หมวดเอง ระบุราคา ต้นทุน SKU/บาร์โค้ด และยอดเริ่มต้น
2. อาหารทำตามสั่งและค่าบริการที่ไม่จำกัดจำนวนให้ปิดการติดตามสต็อก สินค้าคนละขนาดหรือรุ่นให้แยกเป็นคนละ SKU ประเภทและการติดตามสต็อกจะคงเดิมหลังสร้าง
3. แค็ตตาล็อกและราคาใช้ร่วมทั้งองค์กร แต่ยอดคงเหลือแยกสาขา ปุ่ม **แก้ไข** ใช้ปรับรายละเอียด ราคา หมวด หรือเปิด–ปิดขาย การเปลี่ยนจำนวนใช้ **ปรับสต็อก** พร้อมเหตุผล
4. เข้า **POS** เลือกสาขาแล้ว **เปิดกะขาย** ระบุเงินทอนตั้งต้น สาขาหนึ่งใช้กะร่วมกันหนึ่งกะ
5. แตะสินค้า หรือโฟกัสช่องค้นหาแล้วสแกนบาร์โค้ดด้วยเครื่องอ่านแบบคีย์บอร์ดที่ส่ง Enter ปรับจำนวนในบิลได้ ระบบตรวจสต็อกอีกครั้งตอนชำระ
6. เพิ่มชื่อลูกค้า โทรศัพท์ รหัสจอง 8 ตัว หรือหมายเหตุ เช่น ไม่หวาน/ไม่ใส่น้ำแข็ง ตั้งส่วนลดทั้งบิลเป็นบาทหรือเปอร์เซ็นต์
7. **พักบิลนี้** สำหรับรับลูกค้าคนอื่น แล้วเรียกคืนจาก **บิลพัก** บิลพักยังไม่กันสต็อก เก็บเฉพาะหน่วยความจำของหน้าต่างนี้ สูงสุด 20 บิล และหายเมื่อรีเฟรช/ปิดหน้า มีคำเตือนก่อนออกเมื่อยังมีบิล
8. **ไปชำระเงิน** เลือกเงินสด โอน บัตร หรืออื่น ๆ เงินสดระบุยอดรับและดูเงินทอน ส่วนโอน/บัตรต้องตรวจเงินจากธนาคารหรือเครื่องรับบัตรก่อนติ๊กยืนยัน สามารถบันทึกเลขอ้างอิงได้
9. **ยืนยันรับชำระ** ระบบบันทึกขาย การจ่าย และตัดสต็อกพร้อมกัน ตรวจราคาจริงจากฐานข้อมูล หากราคาเปลี่ยนจะย้อนรายการและให้ตรวจใหม่ การลองคำขอเดิมซ้ำใช้รหัสป้องกันบิลซ้ำ
10. หลังสำเร็จ เลือก **ขายบิลถัดไป** หรือเปิด/พิมพ์ใบเสร็จ ใบเสร็จแสดงเงินรับ เงินทอน และอ้างอิงการชำระ เตรียมรูปแบบพิมพ์ 80 มม. ใช้ browser print และต้องตั้งเครื่องพิมพ์ให้ตรงกระดาษจริง
11. **ประวัติบิล** แสดง 100 บิลล่าสุดรวมสาขาที่มีสิทธิ์ กรองสาขา/สถานะ/ค้นหาได้ ยอดวันนี้คำนวณจากฐานข้อมูลครบทั้งวันตามเวลาไทย ไม่ได้รวมจากรายการ 100 ใบนี้
12. ผู้มีสิทธิ์ `confirm_refund` และ `use_pos` สามารถ **คืนเงินเต็มบิลในกะเดิมที่ยังเปิด** ต้องคืนเงินจริงผ่านช่องทางเดิมก่อนยืนยัน ระบุเหตุผลและเลือกว่าจะคืนสินค้าทั้งบิลกลับสต็อกหรือไม่ สินค้าที่ไม่พร้อมขายต่อไม่ควรติ๊กคืนสต็อก
13. **เงินเข้า / ออก** สำหรับเติมเงินทอนหรือนำเงินไปฝาก ระบุยอดและเหตุผล ทุกครั้งบันทึกผู้ทำรายการ ตรวจยอดลิ้นชักไม่ให้ติดลบ
14. **สรุปกะ** ดูยอดสุทธิแยกช่องทาง เงินเข้า–ออก รายการสินค้า และดาวน์โหลด CSV ยอดแยกสินค้าเป็นราคาก่อนส่วนลดทั้งบิล
15. จัดการบิลค้างในหน้าต่างให้ครบ แล้ว **ปิดกะ** นับเงินสดจริง หากขาดหรือเกินต้องใส่เหตุผล ประวัติกะแสดงกะเปิด/ปิดและผลต่างถูกต้อง

## สิทธิ์และความถูกต้อง

- Server actions ตรวจ tenant และสาขาของพนักงานที่ยัง active ก่อนอ่านรายงานหรือเขียนรายการ POS
- คืนเงินต้องมีสิทธิ์เพิ่ม แก้ไขสินค้าใช้ `manage_inventory`
- ขาย รับ/นำเงินออก คืนเงิน และปิดกะล็อกกะเดียวกันเพื่อไม่ให้การปิดกะตัดยอดข้ามรายการ
- เพิ่มสินค้าและยอดตั้งต้นใช้ transaction เดียว หากปรับยอดไม่สำเร็จจะไม่ทิ้งสินค้าไว้ครึ่งรายการ
- คืนสต็อกอ้างอิงจำนวนที่ถูกตัดจริงในบิลเดิม ไม่ใช้สถานะติดตามสต็อกปัจจุบันของสินค้า
- ฟังก์ชันฐานข้อมูลที่เขียนเงิน/สต็อกเรียกได้เฉพาะ service role; client ไม่มีสิทธิ์แก้กะโดยตรง
- รหัสอ้างอิงป้องกันบิลขายซ้ำและรายการเงินสดซ้ำ การเคลื่อนไหวสต็อกทั่วไปยังต้องตรวจประวัติก่อนลองซ้ำเมื่อเครือข่ายขาด
- Modal ใช้ native dialog เพื่อควบคุมโฟกัสและ Escape; UI ใช้สีจาก theme tokens; พิมพ์ใบเสร็จใช้สีสว่างเสมอ

## การอัปเดตฐานข้อมูล

ไฟล์ใหม่: `supabase/migrations/20260913000000_pos_counter_operations.sql`

ต้องมี migration เดิมทั้งหมดก่อน โดยเฉพาะ `20260824000000_pos_inventory.sql`, `20260825000100_pos_shifts.sql`, `20260825000200_fix_pos_shifts_opened_by.sql`

เมื่อเข้าถึง Supabase ได้ ให้ตรวจ project ที่ link อยู่และ migration history, สำรองฐานข้อมูล, ตรวจ `db push --dry-run` แล้วใช้ `db push` ตามลำดับ migration ปกติ ห้าม reset production หรือแก้ migration history เพื่อข้ามไฟล์ที่ล้มเหลว

Migration นี้เพิ่ม metadata การรับเงินใน sales, ตาราง pos_cash_movements และ RPC ของ counter รวมถึงจำกัดการเขียน pos_shifts ให้ผ่าน RPC ไม่มีข้อมูลตัวอย่างหรือการลบข้อมูลธุรกิจ

รอบนี้ **ยังไม่ได้ push หรืออ่านข้อมูล production** สิทธิ์เชื่อมต่อจากรอบก่อนยังไม่พร้อม จึงไม่อ้างสถานะปัจจุบันว่าโปรเจกต์ยัง INACTIVE ผู้ใช้แจ้งว่าเปิดโปรเจกต์แล้ว แต่ยังไม่ได้ตรวจยืนยัน

## UAT ก่อนเปิดใช้จริง

- สร้างสินค้า stock 10 ขาย 2 เหลือ 8 มี sale/payment/movement/receipt ครบ
- ส่วนลดเปอร์เซ็นต์ที่มีเศษสตางค์ ยอดรับตรงยอด และเงินทอนถูกต้อง
- เงินสดไม่พอ ส่วนลดเกินยอด ราคาสินค้าเปลี่ยน สต็อกหมด: ปฏิเสธและไม่ทิ้งรายการบางส่วน
- ส่ง checkout key เดิมซ้ำได้ใบเสร็จเดิม สต็อกไม่ตัดซ้ำ; key เดิมแต่ payload ต่างต้องปฏิเสธ
- สองเครื่องขายสินค้าชิ้นสุดท้าย: สำเร็จได้เพียงรายการเดียว
- เปิดกะพร้อมกัน: สาขามีกะเปิดเพียงหนึ่งกะ ขายขณะอีกเครื่องปิดกะต้องไม่ทำให้ยอดตกหล่น
- คืนเงินพร้อมคืนสต็อก: 8 กลับเป็น 10 ลองคืนบิลเดิมซ้ำไม่เพิ่มสต็อกซ้ำ ยอดขายสุทธิและเงินสดปรับตรงกัน
- คืนเงินโดยไม่คืนสต็อก: จำนวนคงเดิม ดูใบเสร็จบิลคืนเงินได้ กะที่ปิดแล้วคืนไม่ได้
- เติมเงิน 500 นำออก 200: expected cash เพิ่มสุทธิ 300 ปิดกะยอดต่างต้องมีเหตุผล
- พนักงานต่าง tenant/สาขาและพนักงาน inactive ต้องอ่าน/เขียนรายการที่ไม่มีสิทธิ์ไม่ได้
- วันหนึ่งมากกว่า 100 บิล: ยอดวันนี้ยังครบทั้งหมด แม้ประวัติหน้าเคาน์เตอร์แสดงเฉพาะล่าสุด
- Dark/light, จอ 390/768/1440 พิกเซล, แป้นพิมพ์, modal, เครื่องอ่านบาร์โค้ด และเครื่องพิมพ์ 80 มม.

## ขอบเขตที่ยังไม่ครบ SOW / ระดับ POS เชิงพาณิชย์

- SOW §13.3 ต้องการค่าจองสนามและสินค้าในใบเสร็จ/การรับชำระเดียว ปัจจุบันรหัสจองเป็นเพียงการเชื่อมอ้างอิง ยังไม่ได้ดึงค่าจองมารวม ห้ามบันทึกค่าจองซ้ำที่รับชำระไปแล้ว
- การเช่าเป็นรายการคิดค่าเช่า ยังไม่มีทะเบียนยืม–คืนอุปกรณ์ มัดจำ วันครบกำหนด หรือค่าปรับ
- ยังไม่มี split payment, partial refund, คืนเงินข้ามกะ, ภาษี/ใบกำกับภาษีเต็มรูป, เครดิตค้างชำระ, แต้มสมาชิก หรือ promotion engine
- ยังไม่มีครัว/KDS, ตัวเลือกเพิ่มเติมรายเมนู, สูตรวัตถุดิบ, lot/expiry, ใบสั่งซื้อผู้ขาย และ stock transfer UI
- ยังไม่มีบิลพักข้ามเครื่อง/offline sync, เชื่อม EDC/ลิ้นชักอัตโนมัติ, QR ตรวจเงินอัตโนมัติ หรือ gateway refund
- ประวัติบิลและกะมีขอบเขตรายการล่าสุด ไม่ใช่หน้าค้นหาเอกสารย้อนหลังทุกปี
- ไม่ได้ตรวจภาพหน้าจอหรือ E2E จริงในรอบนี้ เพราะ browser access ถูกปฏิเสธ Docker ในเครื่องไม่พร้อม และติดตั้งฐานข้อมูลจำลองไม่ได้เพราะข้อจำกัดเครือข่าย

ห้ามใช้การผ่าน TypeScript/unit tests/build เป็นหลักฐานว่า flow ธุรกรรม production หรือการพิมพ์กับอุปกรณ์จริงผ่านแล้ว

## ผลตรวจอัตโนมัติในเครื่อง

- TypeScript ผ่าน
- ESLint เฉพาะ POS / Inventory และส่วนที่เพิ่ม ผ่าน
- Unit tests ผ่าน 69 รายการ รวม 8 กรณีใหม่ด้านการตรวจ session/สาขา/สิทธิ์คืนเงินและข้อมูลที่ส่งเข้า checkout และ 3 กรณีเงินทอน/ส่วนลด
- Production build ของโค้ดส่งมอบผ่าน (สร้างหน้า static 100 หน้าเสร็จ, exit code 0)
- ไม่ได้ทำ database transaction/concurrency tests หรือ browser E2E จริง ตัวทดสอบ server action ใช้ mock ฐานข้อมูล จึงยืนยันได้เฉพาะขอบเขตตรวจสิทธิ์และการเรียก RPC
